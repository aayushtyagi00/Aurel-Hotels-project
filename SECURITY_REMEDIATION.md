# Security audit verification — 3 November 2026

Reviewed the supplied `SECURITY_AUDIT_REPORT.md` as evidence, rather than treating its proposed patches or conclusions as instructions. Changes apply to this workspace's `aurel` app. The report's other checkout was not modified. Its core API file matched this checkout before changes.

These are local source changes and build/test results, not a claim that production has been secured. No deployment, real booking, real payment, staff grant, or cloud credential change was performed.

| Finding | Verification and action |
| --- | --- |
| SEC-01 Firebase web key | The web key is intentionally public, not a service-account secret. Source cannot establish whether cloud restrictions are absent. Kept Firebase configuration functional; cloud API restrictions still require verification. |
| SEC-02 Owner email/backend URL | Overstated: owner email is server environment configuration, `.env.local` is ignored, and the staff endpoint already requires owner-only permission. Verified email authentication is required before owner authorization. Removed the unused owner field from the staff response. Removed hardcoded production backend defaults; the production build now requires an explicit HTTPS origin. A browser API origin remains observable by design. |
| SEC-03 Inventory flooding | Confirmed missing guest quota. Added a transactional maximum of three active bookings per guest across cities, including paid stays and checked-in stays. Cancellation releases quota. Staff making front-desk bookings retain their existing workflow. Per-guest UID/email locks protect parallel requests; an IP-based Worker booking limiter adds protection. Multiple verified accounts can still abuse a pay-at-hotel business model; deposits, identity checks and CAPTCHA would require separate integrations and policy decisions. |
| SEC-04 CSV | Confirmed whitespace-prefixed formula gap and missing export audit. Replaced browser-generated CSV with an authenticated management-only server export that rechecks role/city scope, creates an audit event in the same transaction, and only then releases the CSV. Escaping covers formula prefixes after whitespace/control characters and quotes. Files still contain personal data and need careful handling after download; normal CSV exports are not intrinsically a vulnerability. Audit records are application-controlled, not immutable against service-account/project administrators. |
| SEC-05 Over-fetching | Confirmed. Resource-specific read plans exclude unrelated collections. Mutations never load historical activity; payment and task mutations target their booking/task, guest reads target ownership, allocation reads competing city/room and guest bookings, public searches query only active reservations overlapping the requested dates and city, and audit reads are database-limited to 200. Added Enterprise dense-index definitions. All queried collections have a 5,001-row detection limit and fail rather than use truncated data. **Partially remediated:** full-history admin reservation/payment/report views still require pagination and aggregation before exceeding 5,000 matching records. The safety limit is not a substitute for that work. |
| SEC-06 Global revision lock | Confirmed. Removed `_system/hotel_revision` writes. Per-room, reservation, guest and payment-booking locks preserve allocation, quota and ledger invariants, including first-use create preconditions. Old/new rooms and guest identities are both locked on edits. Shared catalog and staff reads can still cause transaction contention when those records change. Real Firestore load/concurrency testing remains necessary before production rollout. |
| SEC-07 Deletes | Confirmed latent adapter bug; current room removal already uses soft deletion, so the audit did not demonstrate an existing room-delete exploit. Added before/after deletion detection and native Firestore delete serialization without changing room-history retention. |
| SEC-08 Internal personal data | Confirmed viewer contact/notes and broad task assignee exposure. Viewer hotel reservations now redact guest name, email, phone and notes; payment references and actors are redacted. Housekeeping/maintenance task assignees are limited to the same department within existing city restrictions. Viewer financial totals remain available under the existing reporting permission. Reception still needs guest contacts for operations. |
| SEC-09 Inventory counts | Confirmed the exact count field. Removed `availableCount`; the public contract retains boolean availability. Availability and changing search results inevitably reveal some demand information; this does not prevent all occupancy inference or scraping. |
| SEC-10 External images | Confirmed. New catalog images must be local `/images/` files; previews reject external URLs and API responses replace existing external images with a safe local fallback. This covers existing stored room/reservation images as well as new input. |
| SEC-11 Missing city scope | Confirmed behavior, but it was an explicit legacy compatibility rule, not a demonstrated self-service privilege escalation: staff writes already require an owner and an explicit city setting. Hardened missing/malformed scope to deny all cities; only explicit `null` grants all cities. Existing legacy staff need owner review before rollout. |
| SEC-12 Headers | Confirmed. Added frame restrictions, nosniff, referrer policy, permissions policy and a minimal CSP to Firebase Hosting app paths, API JSON and the Worker response wrapper, including preflight, rate-limit and service-error responses. Hosting rules exclude Firebase-managed `/__/` namespaces so the app frame restrictions do not block its authentication helper iframe. The CSP leaves outgoing frames and popup behavior available for Firebase's sign-in workflow; this is not a full script-source CSP. |
| SEC-13 robots.txt | File was missing. Added private-path crawler directives. This is indexing hygiene, not access control; crawler compliance is voluntary. |
| SEC-14 Rate limits | No application limiter existed; external WAF configuration could not be established from source. Added native Cloudflare bindings: public inventory 120 requests/minute/IP and new bookings 10/minute/IP, with 429/Retry-After and allowed-origin CORS. Counters are approximate per Cloudflare location, not strict global limits. Missing/failing production bindings fail closed with 503. |
| SEC-15 JWT revocation | Confirmed for Firebase account disablement/password resets, but staff permission revocation was already effective on the next request through Firestore. Kept signature/issuer/audience/provider verification and added a current Firebase account lookup. Reject disabled, deleted, unverified, changed-email and revoked sessions using `auth_time` versus `validSince`. Lookup errors fail closed; refreshed tokens from an old authentication session cannot bypass the check. |

## Rollout requirements

1. Verify the browser API key's restrictions in Google Cloud. Allow only the APIs the Firebase client actually uses; do not blindly remove APIs required by enabled Firebase features. Test sign-in, password reset, verification emails and Google sign-in after changes. A publicly visible Firebase key alone does not authorize access to Firestore.
2. Configure `FIREBASE_AUTH_API_KEY` in the Worker with a key for this same Firebase project that permits Identity Toolkit account lookup from the server. It should be restricted to the required API; a browser HTTP-referrer restriction will not work for server requests. The existing web key is used as a compatibility fallback, but this fallback will fail closed if it is browser-referrer restricted. Confirm account lookup succeeds with a real staging token before rollout.
3. Set `FIREBASE_BACKEND_URL` when building the frontend. Development defaults to a local API rather than sending requests to production. Preserve `HOTEL_OWNER_EMAIL` and existing Firestore service-account credentials as server-only configuration.
4. Deploy the Enterprise indexes in `firestore.indexes.json` to the existing `aurel-hotel` database and wait for readiness. Structured queries remain in use because this server adapter needs native read-write transactions; no browser Firestore access or SDK migration was introduced.
5. Ensure the deployment system preserves `PUBLIC_API_LIMITER` and `BOOKING_LIMITER`. They are included in Vite configuration and in the generated Worker configuration. Deploy the Worker and Hosting header configuration, not just frontend assets. Review legacy staff city grants; do not silently convert missing grants to all-city access.
6. Exercise concurrent final-room bookings, same-guest quota races across cities, payment/refund races, and staff revocation against an isolated Firestore staging database. The local hotel fixture serializes transactions and is not a distributed-load test. Plan pagination/aggregation for full-history reports before the 5,000-row limit is reached.
